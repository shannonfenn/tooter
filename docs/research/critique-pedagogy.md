# Adversarial critique: learning UX and pedagogy

> Provenance: produced 2026-07-06 by an adversarial critic subagent during the
> tooter redesign review, reviewing the four proposals in
> [proposals.md](proposals.md) against `docs/pedagogy-for-tutoring.md` and the
> live harness config. Preserved verbatim. Its shared-defect list and
> "terminal-baseline honesty check" fed plan §5–§6 directly.

**Lens:** durable mathematical understanding per hour of the learner's life. Test case used throughout: learner is mid-proof of an AATA Ch. 6 exercise, pen on paper, stuck on "why does gH = Hg matter here?" — followed by a 3–8 turn exchange. Secondary test: a 3-page handwritten attempt at a Ch. 10 quotient-group proof with two crossed-out false starts.

## 1. The actual study loop, minute by minute

**Baseline (terminal, today):** terminal already open. Cmd-Tab → `/hint 6.11 I don't see why gH=Hg is needed at this step` → Enter. ~15–25s to a streaming answer. Follow-ups: just type. The only real costs are (a) reading raw LaTeX and (b) typing any *math-dense* context. This loop is already good. Every proposal must be measured against it, not against a strawman.

- **A (opencode web):** identical action count in a browser tab; strictly adds rendering. Zero added friction *if* the KaTeX rendering claim ("fixed Jan 2026") holds — this is A's single load-bearing unverified link, and its failure floor is the status quo (TUI), which is acceptable. Follow-up turns: unchanged. **Net: baseline + rendering, no new friction.**
- **B (custom app):** same count once the app is running — but "once the app is running" is a new precondition the terminal never had. The context-bound buttons ("Assess" on exercise 4.14's pane) genuinely shave keystrokes off the *ritual* moves. The hidden friction is stochastic: any streaming/session-resume bug lands **mid-proof**, and for this specific user (CS background, solo) the recovery path is "open the app code," which converts a study session into a dev session. That cost never appears in B's LoC accounting.
- **C (JupyterLab):** worst loop of the four, and it recurs every single question. Mid-proof the learner faces a **mode decision each time**: ask in the jupyter-ai side panel, or type into the worksheet cell for 6.11? (Which means first *finding* section 6.11 in the worksheet.) That's +10–30s and a decision tax per question. Worse, C admits chat-panel math rendering is unverified, and its stated fallback — persona writes feedback into notebook cells — is catastrophic for a 3–8 turn rapid exchange: every turn mutates the document, the learner scrolls to locate the new cell, and concurrent edits to an open `.ipynb` invite the classic dirty-buffer/merge problem. A dialogue at cell-append latency is not a dialogue.
- **D (claude.ai):** mid-session, same as A. Session *start* is slower: new chat → tutor must call `get_progress`/`get_due_reviews` and re-orient (~10–20s model time), and per-section disposable chats mean this restart tax recurs often. But D uniquely wins the "stuck at a café / away from desk" loop: photo of the page + one typed line, rendered hint in under a minute, no pipeline. Note this is also where D's state integrity is worst (see §4, §7).

**Photo-as-question (all):** three of the four designs funnel photos into an *assessment* pipeline (A's `/review-paper`, C's `%load_attempt`, B's inbox-attach → assess). But the highest-frequency photo use for a mid-proof learner is "here is my page, here is where I'm stuck, smallest hint" — a *hint* request where transcribe-and-grade is the wrong protocol and where the tutor must be explicitly forbidden from reading past the stuck point (a photo necessarily contains your later scratch work; an eager tutor referencing line 12 spoils the struggle on line 8). Only D's free-form attach naturally supports this, and *no* proposal writes the read-no-further-than-asked rule. This is a missing pedagogy requirement in all four.

## 2. Notation fidelity

**Reading (streaming):** ranked by hardening of *partial* math mid-stream: **claude.ai ≈ assistant-ui/Streamdown (D, B) > opencode web (A; young, one-fix-old) > jupyter-ai chat (C; admittedly unverified) > terminal (none).** For AATA this matters most in long aligned coset/quotient computations and the Ch. 9–11 isomorphism-theorem chains. Flag: **no proposal renders commutative diagrams** beyond AMScd-level `\begin{CD}` (no tikz-cd/quiver anywhere). Diagram-chasing for the isomorphism theorems will live on paper regardless — fine, but nobody should sell "rendered math" as covering Ch. 11.

**Writing:** B's MathLive claim is the dishonest one. This learner has a CS background and a repo full of LaTeX they wrote. For a LaTeX-fluent typist, structured 2-D editing (escaping exponents with arrow keys, selection semantics inside fractions) is *slower* than linear `$\langle a \rangle$` typing; MathLive's payoff is for LaTeX-naïve users and tablets. Prediction: used twice, bypassed forever. B's composer advantage honestly reduces to **live KaTeX preview under a plain textarea** — which *is* valuable (catches `\lange` typos pre-send) and which A and D lack (both render only after send; the tutor echo-confirms instead). C's "snippets palette" is the same gimmick class. **"Photo-first" is a real answer for attempts, only a partial answer for questions** — a question is usually 1 line of typed prose + the page as context, so photo-first plus cheap typed fragments (`Z_12`, `<a>`, tutor echoes proper LaTeX) is the honest input story, and all four can do it; none is differentiated here except by preview.

## 3. Pedagogy affordances

The committed pedagogy (Barton-style diagnostic MCQs, worked-example fading, smallest-hint-first, retrieval-before-help, exit checks, transfer problems) is currently enforced **entirely by prose** in skills/commands. The question is which surface can make any of it *structural*.

- **A:** preserves everything, upgrades nothing. Every discipline stays prompt-enforced, exactly the fragility class that produced the AGENTS.md leak. One regression: rendered output makes **over-answering more damaging** — when the model overshoots the hint ladder (it will), a beautifully typeset full solution is effortless to passively read; raw LaTeX at least imposed a decode cost that sometimes sent the learner back to paper. Rendering raises the stakes on hint discipline while doing nothing to strengthen it.
- **B:** the only design that *can* make pedagogy structural — MCQ answer chips where the explanation is **unrenderable until an answer is committed** (true answer-before-explanation, not honor-system); hint ladders as collapsed rungs (reveal is a learner *action*, logged, so hint-depth becomes a measurable variable per exercise); a "type your attempted definition before Reveal activates" gate for retrieval-before-help. **And B defers every one of these to "later."** As proposed, B's v1 is a pedagogy-neutral nicer chat — it charges the app tax while shipping only A's benefit. If B is built at all, the MCQ-commit widget and hint-ladder reveal are the *only* justification for a custom surface and must be v0, not backlog.
- **C:** notebooks could genuinely do progressive reveal (collapsed cells, ipywidgets MCQ with commit-then-reveal — unmentioned by the proposal), and the worksheet generator **refusing exercises beyond the covered-work boundary is the single best structural-pedagogy idea in any proposal** (covered-work as code). But the delivery loop poisons it: a tutor that teaches by appending cells teaches in monologue-sized units at document latency. Fading and hint-laddering are *conversational* rhythms.
- **D:** worst structural position. You cannot remove claude.ai's product persona; Project instructions fight an assistant RLHF-tuned toward complete, polished helpfulness, and instruction adherence decays over a long chat. Smallest-hint-first will erode by turn 30 of a hard Sylow session precisely when it matters most. This is the AGENTS.md leak class again, inverted: **product defaults leaking into the tutor.** B is the only proposal that fully owns the system prompt; A at least subtracts SWE defaults via geometry.

**Retrieval practice & transfer:** all four rely on the tutor choosing to demand retrieval. Only a session-start mechanism (see §7) makes it happen reliably. Transfer problems (`/transfer-problem`) survive equally everywhere — chat-shaped, no differentiation.

## 4. Assessment integrity (transcribe-first)

The failure to prevent: tutor grades a hallucinated transcription and the learner "learns" from feedback on math they never wrote.

- **Where confirmation is most natural: C.** The transcription lands in an *editable* cell; the learner corrects the LaTeX in place — confirm-by-edit is the strongest confirmation UX in any proposal, and the scan archived beside its feedback is real provenance.
- **Where it's most skippable: D-mobile, then A/D-desktop.** In a single streamed chat turn there is no hard gate between "here's my transcription" and "here's your assessment"; a model that does both in one message is the *default* failure, and A, C, and D all gate it with prose only. D-mobile adds VLM + no state tools + small screen: the learner will thumb "yes looks right" at a 40-line transcription on a phone. **Confirmation fatigue is the mechanism:** for a 3-page proof, an echoed monolithic transcription gets rubber-stamped. The fix nobody proposes: per-page confirmation, uncertainty *highlighting* (model marks low-confidence tokens; learner checks only the marked spans), and — only B can do this — a literal "Transcription confirmed" button that the assessment step is programmatically blocked behind.
- **Crossed-out work:** every proposal copies "ignore cross-outs." Pedagogically half-wrong: the crossed-out first attempt frequently *contains the diagnostic misconception* (the first faulty inference the learner self-caught or didn't). Correct policy: exclude from grading, offer to mine for `misconceptions.md` with consent. No proposal says this.
- **Ledger completeness** (does the attempt actually get recorded?): **B (UI flow can force `record_attempt`) > A ≈ C (command/persona text + schema'd script) > D (tool calls are model-discretionary in claude.ai, no hooks — attempts will silently go unlogged when the model forgets, and always on mobile).**

## 5. Progress & motivation psychology

For a solo adult with no external accountability, the two things a progress surface must do: (1) kill session-start decision cost ("what do I do right now?" → one visible next action + due reviews), (2) *not* manufacture false confidence.

- A visible due-queue + frontier (all four converge on the same YAML/queue design) is genuinely good — implementation-intention machinery.
- **Shared defect, all four:** the `unseen/attempted/needs-review/mastered/retired` per-*exercise* state machine is a category error for proof work. You don't master exercise 6.11; you master the *proof pattern* (coset counting, well-definedness checks). "Mastered" on a proof exercise = false confidence tag; and scheduling a *re-review of the same exercise* at day 21 tests episodic memory of that specific proof, not the schema. The review instrument the pedagogy doc itself implies is a **fresh transfer problem or retrieval prompt on the concept**, generated at review time. A/B/D can do this trivially (the review command generates a fresh prompt); **C structurally cannot without abandoning its thesis** — its stated mechanism is "re-open the worksheet on the 1/3/7/21/60d schedule," which is **institutionalized rereading**, the intervention the testing-effect literature (Roediger & Karpicke; Dunlosky et al. 2013 rate rereading among the lowest-utility techniques) exists to replace. This is C's deepest pedagogical wound: it confuses the *archive* with the *review*.
- Streaks/heatmaps: mild warning for B and C (the surfaces most likely to grow them) — streak pressure selects short computational exercises over multi-evening Sylow proofs. Queue yes, streaks no, "mastered" renamed (e.g., `proved / re-derived / transfers-ok`).
- B's per-session **cost ticker is an anti-feature**: a visible meter shortens exactly the long, flailing sessions proof learning requires (taxi-meter effect). Hide it in a monthly log.

## 6. Distraction and mode-switch costs

- **C is the worst by design.** Its central affordance is a run button. Stuck on "every subgroup of a cyclic group is cyclic"? Enumerating `Z_12.subgroups()` in Sage is one keystroke, feels productive, and *is avoidance* — computation displacing proof is the precise anti-pattern for this book, and C makes it the path of least resistance. Judson's live Sage cells are the author's pedagogy for computational *exploration*; C launders them into an escape hatch from productive struggle. Plus JupyterLab itself is a fiddle garden (extensions, kernels, layout).
- **B is second-worst,** differently: the app is a permanently available, infinitely justifiable procrastination channel for a CS-background learner, and the temptation gradient runs from ego-threatening (stuck on a proof) to competence-affirming (improve my tool). B's own thesis is "prose discipline fails" — yet its scope-creep defense ("feature freeze," "friction log") is prose discipline applied to the *learner's* weakest moment.
- **A and D keep paper primary** by offering nothing else to do. A's static `dashboard.html` and D's chat are dead ends for fiddling. D's phone surface has its own ambient distraction (it's a phone), but that's a cost the learner already pays.

## 7. Session boundaries and memory

The target capability: *"last week you conflated normalizer and centralizer — before we start, define both."* That requires (a) a durable misconception ledger, (b) something that **forces** the tutor to read it and open with retrieval, every session.

- All four converge on state-in-files (YAML/JSONL/misconceptions.md) — correct; long-lived chat context (A's long sessions, D's threads) is the wrong memory substrate for a 12–18 month, 23-chapter pass (context bloat, staleness). Disposable chats + ledger is right — **but only if the session-open ritual is mechanized.**
- **B can hard-code it** (server injects due reviews + top-2 active misconceptions as retrieval prompts into turn one) — strongest. **A** can approximate with a `/start` command or `just study` preamble — but the proposal as written has the pieces and *no ritual*; without it, `misconceptions.md` is a file nobody reads and the normalizer/centralizer move never fires. **D-desktop** relies on instructions to call MCP at chat-open — soft, and decays. **D-mobile is amnesiac and boundary-blind:** no MCP → no covered-work boundary, no misconception history, no due reviews. A café session tutor will cheerfully use Ch. 10 quotient language on a Ch. 4 learner because it cannot see `progress.md`. **C** has no natural session boundary at all (a notebook is always "mid-session"), so the ritual has nowhere to attach.
- **D's second memory hole:** Projects knowledge is fuzzy-retrieved when large. The Pitt↔2021 renumbering (`exercises/verification.md` exists *because numbering is treacherous*) is exactly the fact a RAG chunk drops — tutor assesses "4.27" against the wrong exercise statement. A/B/C read these files deterministically via tools; D must hope retrieval surfaces the right chunk or that instructions reliably force `get_pack_file`.

## 8. Adjudication of the three disputed claims

1. **C: "proof-tutoring wants a persistent executable document" — FALSE for the core loop.** Proof learning is draft → critique → *redraft*; the learning event is the redraft (generation + error correction), and the worksheet's attempt-slot/feedback-slot shape structurally implies completion after one round. The artifact worth keeping is the learner's own final re-derived proof plus the misconception ledger — not the tutor's feedback (low re-read value) and not the dialogue. Execution (Sage) is a verification *sidecar* — the repo's own workflow places it at step 8 of 10. C's true contributions are the boundary-enforcing generator and scan-beside-feedback provenance, both stealable without the notebook medium.
2. **B: "proofs are conversations" — MOSTLY TRUE, with one amendment.** The conversation must *terminate in a learner-produced artifact* (the redrafted proof, on paper, photographed into the attempts archive) or the dialogue evaporates pedagogically. Chat + paper, with the final attempt captured to the ledger, is the right shape.
3. **D: "phone capture ergonomics dominates" — FALSE.** Capture is necessary; *ledger integrity* dominates. A capture loop whose writes reliably land in the state that schedules reviews beats a slicker capture loop that leaks state. D's best-in-class capture feeds its worst-in-class recording path (paste-block sync ritual). Ergonomics that don't reach the ledger are ergonomics for the model, not for the learner's six-months-later self.

## Ranking (expected durable understanding per study hour, full AATA pass)

**A > D > B > C.**

1. **A.** Preserves a loop that already works, adds the two things with unambiguous pedagogical payoff (rendered reading; paper→ledger capture), adds ~zero distraction surface, and its failure mode degrades to the current baseline. Its pedagogy ceiling is low (all prose-enforced), but its *floor* is the highest, and over 12–18 months of solo evenings the floor is what you actually live on.
2. **D.** Best reading + capture ergonomics and genuinely more study *occasions* (phone/voice for conceptual retrieval questions is real). Docked hard for: forked ledger on mobile, boundary-blind café sessions, product-persona erosion of hint discipline, discretionary (unenforced) state writes, RAG-fuzzed exercise identity. Fix the connector and mandate MCP-at-open and D approaches A; as written it trades integrity for polish.
3. **B.** Highest ceiling of all four — the only design that can make answer-before-explanation and hint-laddering *structural* — but the proposal defers precisely those features, and its distraction/maintenance tax is charged in the only scarce currency (learner hours) against a v1 that is functionally A-with-a-nicer-composer. Ranked by the proposal as written, not by its best possible self.
4. **C.** Wrong medium for the core loop (document latency for a dialogic activity), a review mechanism that is literally rereading, a built-in avoidance channel, permanent mode-ambiguity tax, and its two real innovations are portable to any other design. For *proof-based* study specifically, this is the tooling-theater option.

## Strongest hybrid (pure learning outcomes; cost ignored)

- **Tutoring dialogue surface:** B's stack (owned system prompt via Agent SDK + assistant-ui/Streamdown for hardened mid-stream math), **but with the pedagogy interactions as v0, not backlog**. Required features, in priority order: (1) **MCQ commit chips** — explanation physically absent from the payload until an answer + confidence is committed; distractor-mapped feedback per the Barton pattern; (2) **hint-ladder progressive reveal** — one rung per card, next rung behind a learner click, click depth logged per exercise into `attempts.jsonl` (hint-depth becomes an assessment signal); (3) **transcription-confirm gate** — assessment API call blocked until per-page confirm, uncertain spans highlighted; (4) **session-open injection** — server composes turn one from `get_due_reviews` + top-2 active misconceptions rendered as *retrieval prompts*, not statements; (5) **exit-check as a form** whose submission is the only path that advances the covered-work boundary.
- **Capture loop:** D's ergonomics into A's plumbing — phone document-scan → inbox → ledger; **two distinct photo protocols**: `attempt` (transcribe-first, gated assess, record) and `stuck-here` (tutor may read *only up to the indicated point*, responds with rung 1, no grading, no spoiling from the learner's own later scratch work). Desk fallback: Continuity Camera / drag-drop.
- **Review/records:** A's file ledger (per-chapter YAML, append-only `attempts.jsonl`, curated `misconceptions.md`), with C's provenance idea (scan archived adjacent to its attempt record). **Reviews are always freshly generated retrieval/transfer prompts against the due *concept/proof-pattern*, never a reopened artifact.** Retag states: `proved / re-derived / transfers-ok / needs-review` — no "mastered" for proof skills.
- **Progress mechanism:** chapter strip + due queue + single "next action" at session open. No streaks, no cost ticker in-session. Boundary advances only via exit-check.
- **Sage/Python:** stays a terminal/kernel *sidecar* (existing `just`/uv loop); the tutor may *propose* a verification snippet only after a proof attempt exists.

## Terminal-baseline honesty check — what today's setup quietly does right

The redesign must not regress these; several proposals do:

1. **Friction before help = struggle buffer.** Typing math is costly, so the learner batches questions and stays in productive struggle longer before asking. The help-seeking/ITS literature (help abuse, "gaming the system" — Aleven & Koedinger) says cheap help shifts learners from instrumental to executive (answer-getting) help-seeking. Every proposal lowers ask-cost; only structural gates compensate. D lowers it most (phone in pocket) with the least compensating discipline.
2. **No passively readable answers.** Raw monospace LaTeX imposes a decode cost; an over-long tutor answer is *work* to consume, which caps leakage damage. Rendered surfaces remove that cap — rendering must be paired with tighter ladder discipline, or it's a net pedagogical loss on exactly the overshoot turns.
3. **Self-typed notation is retrieval.** Writing `\langle a \rangle`, `\mathbb{Z}_n` by hand is micro-practice of notation fluency. MathLive palettes and snippet pickers remove a small real generation effect. (Photo-first keeps notation practice on paper, which is better still — this defense favors photo pipelines over fancy composers.)
4. **Single channel, nothing to fiddle.** The terminal offers no run button, no extension garden, no app code to improve. A preserves this; C and B sacrifice it outright.
5. **Ephemeral scrollback forces learner-owned records.** Because the terminal keeps nothing nicely, the learner's paper/notes remain the primary record — self-generated summaries are encoding events. C's "keepable worksheet" actively fights this by making the *tutor's* prose the durable artifact.
6. **The `/command` grammar is pedagogical ritual.** `/hint`, `/assess-solution`, `/exit-check`, `/transfer-problem` force the learner to ask in pedagogical categories rather than "help?" — the command names themselves encode smallest-hint-first and the exit ritual. Any new surface must keep these as first-class named moves (D's soft "moves in prose instructions" is the weakest preservation of this).
7. **Permissioned state writes keep the learner witnessing their own ledger** (`edit: ask`) — a small self-monitoring loop that fully-automated state writes (B, D) silently remove; visible `record_attempt` confirmations should replace it.

**Shared defects no proposal addresses** (flagged for the orchestrator): per-exercise "mastered" semantics (wrong unit — schedule concepts/patterns); crossed-out work as misconception evidence (all four discard it); photo-as-question protocol with a no-read-ahead rule; commutative-diagram rendering (unsolvable in v1 — say so honestly and keep diagrams on paper); confirmation fatigue on multi-page transcriptions (per-page + uncertainty highlighting).
